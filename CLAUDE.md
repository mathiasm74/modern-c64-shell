# C64 Shell ROM

A ROM-resident command shell for the Commodore 64, designed to replace the stock BASIC + KERNAL combination with a modern command-line interface. Distributed as a 16KB ROM image suitable for flashing to a OneROM, EasyFlash, or burned EPROM.

## Goals

- Boot directly into a modern shell instead of BASIC's READY prompt.
- Provide a command-line interface with line editing and history.
- Built-in fast loader (Epyx-compatible) for use with stock 1541, SD2IEC, Pi1541, Meatloaf, and 1541 Ultimate.
- File browser and directory navigation for IEC devices.
- Machine language monitor.
- Preserve standard KERNAL entry points so existing machine-language software still works.
- No BASIC interpreter. BASIC programs cannot be run. This is a deliberate tradeoff to reclaim 8KB of ROM space.

## Non-goals

- Running BASIC programs. Use a different ROM slot for that.
- Tape support. The 1530 datasette is not supported; this space is reclaimed.
- GUI or graphics modes. Text only.

## Target hardware

- Commodore 64 (PAL and NTSC).
- Tested in VICE (x64sc) with true drive emulation.
- Final hardware target: OneROM with this image as one of its selectable banks.

## Toolchain

- **cc65 suite** (ca65, cc65, ld65) for assembly and C compilation. Built **from source** (git master, currently `cc3c40c`), installed to `~/.local` (first on PATH, shadows any brew cc65). A released cc65 (<= V2.19) also works but is missing years of codegen fixes — the from-source build is ~150 bytes smaller and fixes [issue #1077](https://github.com/cc65/cc65/issues/1077). **`CC65_HOME` is set by the Makefile** (relative to the cc65 binary) so a non-default-prefix install finds its asminc/lib (`longbranch.mac` etc.); without it the assembler errors. To rebuild cc65: `cd ../cc65 && git pull && make -j4 && make install PREFIX=$HOME/.local`.
  - **`-Cl` (static locals) is ON for the resident shell** (`CC65FLAGS_RESIDENT`), gated on a from-source cc65: the Makefile only adds `-Cl` if `cc65 --version` says `Git`, so a released compiler (<= V2.19, missing the #1077 fix) silently builds without it and stays correct. ~+470 free BASIC-ROM bytes. **Overlays never get `-Cl`** (`CC65FLAGS`): cached/re-run, and outside the 16KB ROM so no benefit. History: `-Cl` on V2.18 hit #1077 (post-increment subscript on a constant-address cast-pointer base with a static `char` index → pre-increment) and corrupted hardware-only paths the suite can't see (garbled `help`, `cd` stage-5, flaky `ls`/`dir`, `8 >` prompt; v0.39–v0.41, reverted). The from-source compiler fixes #1077; `test_cd` (the canary) passes with `-Cl` on it, and it was re-enabled in v0.43. If you ever see that class of corruption again, confirm `cc65 --version` shows a `Git` build.
- **VICE** (x64sc specifically) for emulation and testing. Version 3.7 or later.
- **Python 3** for the test harness.
- **GNU Make** as the build driver.

All tools must be on PATH. Verify with `make check-tools`.

## Build

```
make             # builds build/kernal.bin and build/basic.bin
make test        # builds and runs the test suite
make run         # builds and launches VICE with the ROM
make onerom      # builds a (single-bank) One ROM firmware image from both halves
make onerom-stock # builds the stock-fallback (host-control) firmware
make onerom-flash # builds + flashes the stock-fallback firmware, then reboots it
make sizes       # per-command ROM code-size report (tools/cmd_sizes.py)
make clean       # removes build artifacts
```

`make sizes` (`tools/cmd_sizes.py`) assembles the command modules with a ca65 listing, measures each function from its `.proc` marker, and walks the jsr/jmp call graph to attribute helper code to commands -- reporting each command's *exclusive* cost (body + helpers only it reaches), the *shared* helpers (reached by 2+ commands, e.g. `launch_stock_program` for run+basic), and whether the command is resident or just an overlay thunk. Use it to decide what's worth moving into an overlay.

The build produces two 8KB binaries that together form the 16KB ROM:
- `build/kernal.bin` maps to $E000-$FFFF.
- `build/basic.bin` maps to $A000-$BFFF (despite the name, this is not BASIC; it's the shell code).

For a raw 16KB blob (EPROM/EasyFlash) the two are concatenated: `cat build/basic.bin build/kernal.bin > build/rom16k.bin`.

### One ROM firmware

`make onerom` builds a flashable [One ROM](https://onerom.org/) firmware image with the `tools/onerom` CLI (a Mach-O universal binary, kept untracked — it's ~10MB). It reads `cfg/onerom.json` and writes `build/onerom-<board>.bin`. The config has **two slots**:

- **Slot 0:** the USB *system plugin* (`https://images.onerom.org/plugins/system/usb/v…/plugin.bin`, fetched/cached on build). Without it the device can't accept USB commands once it's serving ROM, so `onerom reboot` would refuse with *"does not support being rebooted into running mode."*. To bump the plugin version, edit the URL in `cfg/onerom.json` (or regenerate with `tools/onerom firmware build --plugin usb --save-config …`).
- **Slot 1:** both ROM halves as one multi-ROM set — `kernal.bin` and `basic.bin` as two 2364s served by the `two_cs_one_addr` algorithm. Two active-low chip selects (the C64's KERNAL `/CS` at U4 and BASIC `/CS` at U3) over the shared A0–A12 bus. (A single CS line can't distinguish KERNAL vs BASIC vs neither, so it genuinely needs both selects; the One ROM CLI also rejects mixing active-low/active-high in one set.) ROM order in the config is the CS-pin order — `kernal.bin` first, `basic.bin` second.

The board defaults to `fire-24-e`; override for your hardware: `make onerom ONEROM_BOARD=fire-28-a` (`tools/onerom scan --list-boards` lists them). **`make onerom-flash` flashes the stock-fallback firmware** (`cfg/onerom-stock.json`, the same image `make onerom-stock` builds), then reboots the device into the running (byte-serving) state in one step; set `ONEROM_SERIAL='5*'` to pick one of several. `onerom scan` after that should show **Running** instead of Stopped. (The plain single-bank `cfg/onerom.json` image that `make onerom` builds has no host-control plugin, so the device refuses the reboot-into-running step -- which is why `onerom-flash` uses the stock config. `make onerom` remains build-only for inspection.)

**C= boot menu (GRUB-style):** the `onerom-stock` firmware's loadable ROM **set 0** is r107sl's `c64-bootloader` (vendored at `third-party/c64-bootloader/`, MIT, built from source by `tools/build_bootloader.sh` — NOT the pre-built binary Piers hosts, whose v0.1.0 predates firmware 0.7.x and fails `GET_FLASH_SLOT_INFO_ALL`). At One ROM cold boot it shows a menu (hold **C=**, RUN/STOP, or Q) to pick a kernal, else auto-boots the last choice (remembered in NV). Set order (labels via each set's config `label`): **0** bootloader, **1** Tardis DOS (boot default), **2** stock C64, **3** JiffyDOS, **4/5** overlays_a/b, **6** Tardis+Swedish (font B), **7** overlays_c. The menu **hides sets 4–7** (a small `LOCAL PATCH` in the vendored `main.c` clamps the list at the first `~`-labelled set; those sets carry `~`-prefixed labels). Hiding the Swedish set is deliberate — booting it directly gives an English font (reset.s's boot normalize always reloads font A), so Swedish is reached via `font 1` (persisted in NV), not the menu. Two cc65/C64 gotchas the patch documents: read the back-channel `rbcp[]` through a **volatile** pointer (it's `const`, device-filled at runtime, else the read folds to 0) and compare against the **raw ASCII byte `0x7E`**, not `'~'` (cc65 `-t c64` PETSCII-translates char literals → `$B1`). **Holding C= from a running shell also returns to the menu** (`_rbcp_launch_bootmenu` in launch.s: re-serves flash set 0 and resets into it) — the One ROM keeps serving the picked set across a bare C64 reset while powered, so set 0 would otherwise only be reachable by a full One ROM power-cycle. This replaced the old direct C=→stock shortcut (stock is a menu entry now). RBCP slot constants moved with the new layout: stock = flash set **2** (`RBCP_STOCK_FLASH_SLOT`), font B = set **6** (`FONTB_FLASH_SET`), bootmenu = set **0**; overlay set numbers are generated (`tools/gen_overlay_pages.py`). The NV settings blob moved to **offset 16** (`NV_BLOB_BASE` in launch.s / `restore_colors` in reset.s) so it clears the bootloader's own last-boot byte at NV offset 1. To fit the new KERNAL-half asm under the `$FE00` back-channel window, `cmd_font` moved from CODE2 to the BASIC half. Hardware-only to validate (RBCP swaps are inert in VICE); confirmed working v0.1.75. Boot defaults are now **dark-red bg ($02) + light-red border ($0A)** (was brown/orange; `test_memory.py`).

**Commodore 128 (C64-mode) port — `make onerom-c128`:** Tardis runs on a flat C128 as the **C64-mode ROM in socket U32**, so `GO64` gives the shell while C128 mode stays 100% stock. U32 holds the `325182` (a 16KB 23128 = `[C64 BASIC $A000 | C64 KERNAL $E000]`, the two 8KB halves served to two non-contiguous CPU windows); Tardis's own `build/rom16k.bin` (`basic.bin`+`kernal.bin`) is a drop-in for that exact layout. The One ROM (fire-28-c) replaces the chip; the C64C `28-c64c.json` CS values apply (`cs1/cs2=active_low, cs3=active_high` — same CBM 23128 mask). Built by `tools/build_c128.sh` (compiles the shell with `-D TARGET_C128`, packs the 16KB served image + overlay flash sets + a stock-C64 set for the One ROM). Key pieces of the port:
- **`TARGET_C128`** (build flag) does three things. (1) `reset.s`/`shell.c`: **skip all boot-time RBCP** (slot-normalize, NV colour restore, boot-device probe, C= menu, cartridge swap) — the boot-menu/font/NV features don't apply and their handshake **hangs before display-on** (white screen). (2) `rbcp_config.s`: **remap the RBCP command page to `$A0`** — the plugin watches image offset 0, which in the 16KB U32 image is `$A000` (BASIC half), not `$E000`; the back-channel stays `$FE00` but its ROM offset is set explicitly to `$3E00` (KERNAL is the 2nd 8KB, a different CPU window than the command page, so the linear formula is wrong). (3) `launch.s`: `RBCP_STOCK_FLASH_SLOT=4` (the stock-C64 set's loadable index here). `tools/gen_overlay_pages.py` emits overlay sets **1/2/3** (env `OVL_C128=1`, set by the Makefile) to match the U32 firmware layout: loadable set **0** Tardis (served), **1/2/3** overlays_a/b/c, **4** stock C64 (`325182` from Zimmers, what `basic`/`run` swap to).
- **VIC-IIe IRQ fix (unconditional, helps the C64 too):** `reset.s` now disables+clears the VIC IRQ (`$D01A`/`$D019`). The C128 uses VIC raster IRQs in 128 mode and `GO64` carries one into C64 mode still enabled; Tardis's handler only acks CIA1, so it re-fired forever and **livelocked** the machine (banner drew, `main()` starved → no prompt).
- **0.7.x RAM-slot sizing:** the served image is a single 23128 (16KB), so RAM slots are 16KB; the 8KB overlay sets are **`size_handling=duplicate`** to 16KB or `LOAD_SLOT` refuses them.
- **Overlay commands work** on the C128 exactly as on the C64 (fetched over RBCP with the remapped command page); `basic`/`run` swap to the stock-C64 set (power-cycle to return to Tardis). **Flashing gotcha:** the One ROM needs a true **power-off cold boot** to serve cleanly (an `onerom reboot` into running left it dark) — `onerom-c128-flash` programs without a reboot and tells you to power-cycle by hand; and it shares the `build/` tree with the C64 build, so `make clean` before a plain build. The whole RBCP path is hardware-only (inert in VICE); validated on a real flat C128, 2026-09-04.

**Commodore 64C port — `make onerom-c64c`:** the cost-reduced C64C carries KERNAL+BASIC as a **single combined 16KB ROM** (`251913` = `[C64 BASIC $A000 | C64 KERNAL $E000]`) in one 28-pin socket, so a **28-pin One ROM** (default `fire-28-a`) replaces it. This is the reason the normal `make onerom-stock` (breadbin, `fire-24-e`) can't target a 28-pin board: the breadbin's KERNAL (U4) and BASIC (U3) are **two separate 24-pin 2364s**, served as a **multi-ROM set over two chip-selects**, which needs the One ROM's **X1 pin** — and the 28-pin boards' headers have no X1 (`fire-28-a` has none; `fire-28-c` has X1/X2 but its 2364 select GPIOs aren't contiguous for that chip type). A single combined chip is one CS, no X1 — so `fire-28-a` serves it (and the loadable overlay sets) fine. The C64C image/layout is **identical to the C128 U32 case**, so `tools/build_c64c.sh` **reuses the `TARGET_C128` build mode** (which is really "single combined ROM image" mode, not C128-machine-specific: command page remapped to `$A000` = image offset 0 of a `[BASIC|KERNAL]` image, stock-swap set at flash slot 4, and boot-time RBCP skipped because its handshake hangs before display-on on the combined layout). The served set 0 is Tardis `rom16k` as one `23128` with the CBM 23128 CS mask (`cs1/cs2=active_low, cs3=active_high`); sets 1–3 are the overlays (duplicated 8KB→16KB); set 4 is genuine stock C64 `[BASIC|KERNAL]` (from `stock-roms/`) that `basic`/`run` swap to. **No char ROM is served** (a 2nd chip would reintroduce the multi-CS/X1 need), so **`font` fails** ("font switch unavailable") — deliberate. Everything else works: overlays fetch over RBCP at command time; `run`/`basic` swap. Board override: `make onerom-c64c C64C_BOARD=…`; `onerom-c64c-flash` programs without a reboot (like the C128, wants a power-off cold boot) and tells you to power-cycle. Shares the `build/` tree (compiles with `TARGET_C128`), so **`make clean` before a plain breadbin build**. **NOT yet validated on real C64C silicon** — only in C128 C64-mode, the same combined-ROM path; sanity-check boot + a couple of overlay commands after flashing.

`make run` delegates to `./run.sh`, which builds the ROM (unless `SKIP_BUILD=1`) and launches `x64sc -kernal build/kernal.bin -basic build/basic.bin`. Run `./run.sh` directly to forward extra VICE arguments, e.g. `./run.sh -warp`. To try the disk commands, attach an image with `DISK=`: `make run DISK=test/data/test.d64` (or `DISK=... ./run.sh`). It mounts a fresh writable *copy* (`build/run-disk.d64`) with `-drive8truedrive`, so a session's `cp`/`rm` never mutate the tracked image. True drive emulation is required — we replaced the KERNAL, so VICE's virtual-device traps never fire. Without a disk, typing `ls` reports a read error after a short timeout rather than wedging.

## Conventions

### Code organization

- **Hardware setup, IRQ handler, and KERNAL entry points are in assembly** in `src/*.s`. These are timing-sensitive or need fixed addresses.
- **Shell logic, parser, and command implementations are in C** in `src/*.c` and `src/commands/`.
- **Fast loader is in assembly** in `src/fastload.s`. Timing matters too much for C.
- C code calls assembly via standard cc65 calling conventions. Assembly that needs to be called from C is declared with `.export _name` and accessed in C as `name()`.

### KERNAL entry points

Standard KERNAL routines must exist at their published addresses for compatibility:

| Address | Routine  | Purpose                          |
|---------|----------|----------------------------------|
| $FFD2   | CHROUT   | Print character in A             |
| $FFE4   | GETIN    | Read character (non-blocking)    |
| $FFCF   | CHRIN    | Read character (blocking)        |
| $FFBA   | SETLFS   | Set logical file params          |
| $FFBD   | SETNAM   | Set filename                     |
| $FFC0   | OPEN     | Open file                        |
| $FFC3   | CLOSE    | Close file                       |
| $FFC6   | CHKIN    | Set input channel                |
| $FFC9   | CHKOUT   | Set output channel               |
| $FFCC   | CLRCHN   | Restore default channels         |
| $FFD5   | LOAD     | Load file                        |
| $FFD8   | SAVE     | Save file                        |

These are JMPs to implementations elsewhere in the ROM, placed at their fixed addresses by per-entry segments in `cfg/rom.cfg` (`STUB_FILE_IO` $FFBA-$FFD1, `STUB_CHROUT` $FFD2, `STUB_LOAD_SAVE` $FFD5, `STUB_GETIN` $FFE4). Defined in `src/kernal_stubs.s`. The file-I/O entries are thin shims over the `iec_*` primitives in `iec.s`: SETLFS/SETNAM record params into the KERNAL-standard zero-page (LA $B8, FA $BA, SA $B9, FNLEN $B7, FNADR $BB/$BC); OPEN/CLOSE/CHKIN/CHKOUT call the matching `iec_*` routine; CLRCHN releases any held IEC channels and restores DFLTN=0/DFLTO=3; CHRIN reads from `iec_getbyte` if DFLTN >= 8, else blocks on the keyboard via GETIN. LOAD forces bus channel 0 (the load channel) regardless of SETLFS's SA — SA only decides whether to honor the file's embedded load address (SA=0, the BASIC LOAD convention) or use the X/Y override (SA!=0). CHRIN preserves X and Y per the standard so callers can use a register as a loop counter (the underlying `_iec_getbyte` clears them as part of cc65's fastcall return). CHROUT ($FFD2) routes by DFLTO: screen normally, the IEC channel after CHKOUT — with the stock KERNAL's one-byte deferral (WRPEND $94 / WRBYTE $02BE) so CLRCHN can send the final byte with EOI and the drive finalizes the file instead of leaving a splat. Single-file model: we don't keep a per-LFN open-file table; the most recent SETLFS values are the implicit "current" file. `test_kernal_io.py` writes ML stubs into RAM and invokes them with the harness's `run_at(addr, seconds)` to exercise each entry end-to-end. **CHROUT** ($FFD2 -> `chrout_impl` in `src/screen.s`) and **GETIN** ($FFE4 -> `getin_impl`) date from Phase 3.

### Zero page

The C64 normally reserves $00-$8F for BASIC and $90-$FF for KERNAL. Since we have no BASIC, $00-$8F is available to the shell. cc65 uses $02-$1F by default for its pseudo-registers; configure this in `cfg/rom.cfg`.

Reserve $90-$FF for KERNAL working storage and keep it compatible with documented usage so loaded programs that poke around in zero page don't break. Locations in use, all at their standard KERNAL addresses:

- `$90` I/O status (ST), set by the IEC routines (EOI $40, device-not-present $80)
- `$A0-$A2` jiffy clock (TIME), advanced by the IRQ handler
- `$94/$95` IEC byte buffer (BSOUR), `$A3-$A5` IEC bit count / filename index / EOI scratch
- `$B7` filename length (FNLEN), `$B9` secondary address (SA), `$BA` device (FA), `$BB/$BC` filename pointer (FNADR)
- `$C5` last key matrix code (LSTX), `$C6` keyboard buffer count (NDX)
- `$D1/$D2` current screen line pointer (PNT), `$D3` cursor column (PNTR), `$D6` cursor row (TBLX)
- `$F3/$F4` current color line pointer (USER), `$F5/$F6` CHROUT register save
- `$F7-$F9` keyboard-scan scratch, `$FB-$FE` reset's string-drawing pointers
- `$0277-$0280` keyboard buffer, `$0286` current text color

The keyboard-scan scratch ($F7-$F9) is deliberately disjoint from the CHROUT/cursor locations so an IRQ-driven scan can't corrupt a CHROUT in progress.

### Naming

- Assembly labels: lowercase with underscores, e.g. `init_vic`, `scan_keyboard`.
- C functions: lowercase with underscores, e.g. `parse_command`, `cmd_ls`.
- Constants in assembly: uppercase, e.g. `SCREEN_RAM = $0400`.
- Command handlers in C: `cmd_<name>`, e.g. `cmd_help`, `cmd_load`.

### Commits

Commit after every passing test. Each commit should leave `make test` green. Use short imperative subject lines: "add CHROUT entry point", "implement ls command", not "Added the CHROUT entry point".

### Version

**Bump the version on every build handed to the user** so they can tell on-screen which build they flashed. The scheme is `v0.<minor>.NN`, always **7 chars** `"vX.Y.ZZ"` (rolled `v0.1.99` -> `v0.2.00` at the bank architecture; keep the width or the right-aligned banner column shifts). It lives in two source places kept in step: `src/reset.s` (the `version` string in the boot banner, e.g. `"v0.1.48"`, drawn top-right — right-aligned starting at col 32 so its 7 chars end at col 38; widen/shift that column if the string length changes) and `src/commands/builtins.c` (`ver` command, `"Tardis DOS v0.1.48"`). Only `test_builtins.py::test_ver_prints_version` asserts the exact string (other boot/dispatch checks match the version-agnostic `"Tardis DOS v"`, and several tests use `ver` as a "shell alive" sentinel by waiting for `"Tardis DOS v"`), so a bump touches those three lines. The shell is branded **Tardis DOS** ("bigger on the inside" — the tardis-overlay architecture); the boot banner is centered: row 0 version (right-aligned), row 2 `"Tardis DOS - your C64 power shell"`, row 4 the `Free ROM bytes: BASIC ---- KERNAL ----` line (the two `----` are build-patched by `tools/patch_freemem.py`), row 6 `Ready.`, row 7 the prompt.

## Testing

The test harness lives in `test/lib/vice.py`. The `Vice` class is a context manager that launches `x64sc` (headless via `-console`), connects to the text remote monitor on a free TCP port, and exposes the machine:

- `read_memory(addr, count)` / `read_byte` / `write_memory(addr, data)` / `write_byte`
- `screen_text()` / `screen_rows()` / `screen_cells()` (screen codes decoded to ASCII)
- `registers()` / `pc()`
- `inject_keys(text)` (writes the keyboard buffer at $0277 and the count at $C6)
- assertions: `assert_screen_contains`, `assert_memory_equals`, `assert_pc_at`, `assert_display_enabled`

A test is a function `test_<name>(v)` in a `test_*.py` module that asserts on the
passed-in `Vice`. `test/run_tests.py` discovers the modules, runs every test
function (one fresh VICE per module, for isolation), and prints a pass/fail
summary. `make test` runs it headless; modules run **in parallel** (one VICE each,
up to 6 workers -- more flakes the timing-sensitive drive tests; `VICE_JOBS=1`
restores serial for debugging), scheduled longest-first from the previous
run's per-module times (`build/test-times.json`), and each module's wall time
is printed for spotting slowpokes. **Fast iteration: `make test M=<substr>`**
runs only the modules whose name contains the substring(s) (`M="disk rm"`
works too) -- the full suite is ~35s, a single module is seconds. Prefer
polled waits (loop `run_for` until the expected text appears) over long fixed
sleeps -- VICE runs `-warp`, so completion usually beats the timeout by a lot.
When injecting keys and waiting for them to be consumed, poll NDX ($C6) back
to zero rather than sleeping a fixed interval (see test_edit's `_keys`). The
harness's `_drain` is prompt-aware (returns at the trailing `(C:$xxxx) `
instead of waiting for a quiet gap) -- this is what makes per-command monitor
round-trips ~ms; if VICE's monitor prompt format ever changes, update
`_PROMPT_RE` in `test/lib/vice.py`.
`make test-verbose` (or `VICE_VERBOSE=1`)
shows the launch command, monitor traffic, and tracebacks. `VICE_HEADLESS=0`
opens the GUI window for debugging.

Screen memory at $0400-$07E7 contains C64 *screen codes* (display codes), which are not the same as ASCII/PETSCII. The shell boots in the lowercase/text charset ($D018 = $16, charset @ $1800) with an ASCII-consistent encoding (`pet2scr` in `src/screen.s`): lowercase 'a' is byte $61 -> screen code $01, uppercase 'A' is $41 -> screen code $41. Use `screen_text()` / `screencode_to_ascii` in `test/lib/vice.py` for assertions; that decoder mirrors the same charset. Note: `screenshot()` only works with a real video device, not in headless `-console` mode.

When adding a new feature, add a test that exercises it. The test suite is the safety net that lets us refactor confidently.

## Working with this codebase

- The reset vector at $FFFC/$FFFD must point to the init code in `reset.s`. Don't move this without updating the linker config.
- The IRQ vector at $FFFE/$FFFF must point to the IRQ handler in `irq.s`.
- When implementing a new command, add it to the dispatch table in `src/shell.c` and create a handler in the appropriate `src/commands/*.c` file. The dispatch table is kept sorted alphabetically and lives in the `RODATA2` segment (`#pragma rodata-name`), which `cfg/rom.cfg` loads into the KERNAL ROM rather than the smaller BASIC ROM where the rest of the cc65 output sits. `cmd_help` (which prints the commands in three indented 12-wide columns, column-major over the sorted table, then two lines advertising the line-editor features nothing else does -- "Tap CTRL to complete a file name." and "Cursor up/down recalls commands."; completion especially, since the C64 has no TAB key and the CTRL-tap binding is otherwise undiscoverable) lives in `CODE2` for the same reason. Other things can be relocated to KERNAL via the same pragma pair when the BASIC ROM gets tight.
- When adding a KERNAL entry point, update both `src/kernal_stubs.s` and the table in this document.
- Run `make test` before committing. Beware make's one-second mtime granularity: a scripted source edit landing in the same second as the previous build silently skips the rebuild (tests then run a stale ROM -- seen as "impossible" failures like an old version string). `make clean` when in doubt.
- Run `make test` before committing. If tests fail, fix them or mark them as expected failures with a comment explaining why.
- Prefer adding new tests over modifying existing ones. Existing tests document expected behavior; changing them silently can hide regressions.

The corpus showed quickly that with the shell ROM as the only environment, real C64 software mostly fails — it expects stock BASIC/KERNAL bytes we don't (and can't economically) reimplement. The architectural answer is to **hand off to stock ROMs at program-launch time**, via the [One ROM Bus Control Protocol](https://github.com/piersfinlayson/rom-bus-control-protocol) (`user/host-control` plugin). The 6502 reference library is now vendored at `src/rbcp/` (assembled into a `RBCP_CODE` segment in KERNAL ROM where we have slack), with `src/rbcp/rbcp_config.s` tailored for our memory map (command page at `$E0`, back-channel at `$E100-$E2FF`, ZP block at `$80-$8F`). `cfg/onerom-stock.json` adds the host-control plugin (slot 1) and a stock-ROM chip_set (slot 3); stock C64 ROMs live in `stock-roms/` (gitignored, user-supplied). `make onerom-stock` builds the 4-slot firmware. The RAM-resident trampoline that drives the bank swap is in `src/rbcp/launch.s`: `_rbcp_launch_stock` (KCODE) copies the whole RBCP_CODE block from ROM to RAM at $C800, patches the trampoline's final `JMP $0000` operand with the entry address, and `JMP`s into the in-RAM trampoline; the trampoline then `SEI`s and drives `rbcp_reset → enter_cmd_resp → load_slot (3 → RAM slot 1) → switch_and_exit → JMP entry`. `cmd_runstock` (fs.c, in CODE2 to fit the BASIC ROM budget) is the C-side glue. `test_rbcp.py` verifies the segment layout and that the launcher does the right copy/patch (the actual swap is unobservable in VICE since the One ROM model isn't emulated). See `docs/RBCP-DESIGN.md` for what still needs hardware validation.

**Character ROM + the `font` command:** the One ROM can also serve the C64's character ROM (socket U5) on a 3rd chip-select (the char `/CS`, wired to a spare One ROM CS input). The One ROM serves **one set at a time, max 3 ROMs per set** (3 CS lines), so the char ROM rides as the 3rd ROM in the same served set as KERNAL+BASIC. Two switchable fonts = two full sets that carry **identical KERNAL/BASIC** plus a different char ROM, so live-switching between them doesn't disturb the running CPU (it sees the same KERNAL/BASIC bytes; only the font the VIC reads changes). `cfg/onerom-stock.json` loadable sets: **0** = shell KERNAL+BASIC+`c64-charset` (boot/font A), **1** = stock+charset, **2/3** = overlays_a/b, **4** = shell KERNAL+BASIC+`c64-swedish4` (font B). The char ROM is declared `Chip2364` + `"size_handling": "duplicate"` (a 4K image mirrored into 8K -- a real 2-CS 2332 can't share a set with the 1-CS 2364 KERNAL/BASIC; the char socket only drives A0-A11, so duplicate makes A12 irrelevant). `font [0|1]` (resident, `fs.c`, CODE2; no arg toggles) live-switches via RBCP **`SWITCH_SLOT`** (the new `rbcp_cmd_switch_slot` wrapper + `_font_apply` trampoline in launch.s): to font B it `LOAD_SLOT`s set 4 into **RAM slot 2** (NOT the served slot 0, which would rewrite live KERNAL/BASIC and crash) then `SWITCH_SLOT`s to it; to font A it just `SWITCH_SLOT`s back to RAM slot 0 (still holding font A). `font_current` (resident BSS, 0 at boot) tracks state so it never LOADs the served slot. **`BASE_SLOT` (`$02CE`) records which RAM slot the base is currently served from** (font A = 0, font B = 2), because it is NOT always 0 -- and `bank_restore` (launch.s) switches back to *that* after a bank command. It used to assume slot 0, so **any bank command (`ls`, `dir`, ...) silently reverted font B to font A** while leaving `KBD_LAYOUT` on Swedish: the keys still emitted `$5B/$5C/$5D` but the US charset drew them as `[ ] £` instead of `ä ö å` (hardware-reported, fixed v0.1.94; `reset.s` clears `$02CE` at boot -- page-2 RAM is power-on garbage, the same hazard it already guards for `KBD_LAYOUT`, and `test_font` checks it). **Known remaining effect:** the bank's own flash set carries the US charset, so the glyphs flip to US *for the duration of* a disk command and return afterwards; fixing that would need a second bank set carrying the Swedish charset, selected by `font_current`. RBCP-only -> "font switch unavailable" without a One ROM (`test_font.py`). **HARDWARE-VALIDATE the RAM-slot assumptions** (boot serves slot 0, slot 2 free, slot 1 stays overlay/stock scratch) -- the `FONT*_RAM_SLOT`/`FONTB_FLASH_SET` constants in `fs.c` are the single place to adjust them. Known edge: a soft `reset` (not a power cycle) after a font switch can desync `font_current` from the still-served font (the One ROM keeps serving slot 2); recover with a power cycle.

**Swedish keyboard (paired with font B):** the keyboard layout is tied to the charset, and the question "is key->code the same, only code->glyph different?" is **no -- both differ**. The Swedish charset (`c64-swedish4.bin`) draws lowercase **ä ö å at screen codes $1B/$1C/$1D** (the `[ \ ]` slots) and uppercase **Ä Ö Å at $5B/$5C/$5D** (verified by rendering the actual file's bitmaps). Tracing back through `pet2scr` (`src/screen.s`): lowercase come from PETSCII **$5B/$5C/$5D** (the existing `-$40` rule); uppercase needed a new `pet2scr` branch mapping **$DB/$DC/$DD -> $5B/$5C/$5D** (the standard `-$80` rule, = lowercase code + $80). Producing those codes from a physical Swedish keyboard also needs a **second decode table**: `irq.s` gains `keytab_se`/`keytab_se_shift` (clones of the US tables with the symbol cluster + 3 letter keys remapped per the real Swedish keycap layout -- matrix 46/45/50 = Ä/Ö/Å, with `@`/`:`/`*`/`;`/`+` relocated to stay reachable; `[ ] £` become the letters). The scan selects the table via the `KBD_LAYOUT` byte ($02CB, 0=US/1=SE) through `decode_unshift`/`decode_shift` (ROM tables can't be self-modified, so it branches on the byte rather than patching the load operand). `cmd_font` sets `KBD_LAYOUT` = target alongside the charset swap, so `font 1` flips glyphs and keyboard together; `reset.s` clears it to 0 (US) at boot. **Input plumbing for the high bytes:** the uppercase Swedish codes $DB-$DD are above the usual printable window, so two filters had to widen to pass them: `readline` (`shell.c`, `SWE_LO`/`SWE_HI` = $DB/$DD) stores/echoes them, and `chrout_impl` (`screen.s`) draws $DB-$DD (it otherwise ignores $80-$FF) -- without both, shift-Å/Ä/Ö emitted the right byte but it was dropped on the way to the screen. The decode tables + the `pet2scr` mapping + the readline/chrout acceptance are checked in `test_swedish.py` (table bytes read from ROM via labels.txt; `pet2scr` via an ML stub; a typed $DB lands as screen code $5B -- this last test reboots via the reset vector first because the prior `run_at` test parks the CPU) -- VICE-testable even though the live matrix and the `font`-driven activation are hardware-only. **HARDWARE-VALIDATE the matrix positions** on the real Swedish keyboard; the `keytab_se`/`keytab_se_shift` bytes in `irq.s` are the single place to adjust if a keycap lands on a different matrix code. The selected font (and thus the Swedish layout) **persists** across a power cycle via NV (see below); known limit: uppercase Å Ä Ö render only in the shell's lowercase charset (which is what it always uses).

**Swedish keyboard under the STOCK ROMs (after a `run`/`basic` swap):** the stock KERNAL has its own keyboard decode tables ($EB81 unshift / $EBC2 shift, confirmed in `kernal.901227-03.bin`; a pointer table at $EB79 selects them), so after the One ROM swaps to the stock ROMs they'd be US. When font B is active, the swap trampoline (`src/rbcp/launch.s`, gated on `KBD_LAYOUT` $02CB == 1) patches them in place via RBCP **`SLOT_POKE`** (group MODIFY $02 cmd $00; new `rbcp_cmd_slot_poke` wrapper in `rbcp.s`): after `load_slot` puts the stock set in a RAM slot but **before** `switch_and_exit`, it pokes the **8 cells per table** that differ from US (the `+ - @ * : ; =` cluster + the 3 letter keys) — 16 single-byte pokes from the `se_kbd_off`/`se_kbd_byte` tables (offsets $0B81+n / $0BC2+n since the served slot is KERNAL-first; bytes match `keytab_se`/`keytab_se_shift` at matrix indices 40,43,45,46,48,49,50,53). The A–Z keys stay stock uppercase PETSCII (the Swedish letter codes $5B/$5C/$5D / $DB-$DD are convention-independent, so they drop straight in). **Why poke-at-swap, not a pre-patched flash set (Approach A):** A would need one full stock set per language (kernal+charset+basic), a combinatorial flash blowup; the poke needs **one** stock set + a small per-language patch table. **Why poke-every-swap, not once at `font`:** `SLOT_POKE` writes a RAM slot (volatile, reloaded from flash at boot) and RAM slot 1 is the shared overlay/stock scratch, so a font-time poke would be lost on power-off and clobbered by the next overlay — re-applying at each swap is the robust equivalent of how fonts re-apply at boot (the *choice* persists in NV; the bytes are re-applied automatically, so it's persistent from the user's view). If the plugin doesn't implement `SLOT_POKE` the poke loop bails on carry-set and boots stock **US** (never wedges the swap). **Keyboard only** — the served stock set still has the US charset, so Ä Ö Å produce the right *codes* but not the right *glyphs*; correct display + true in-flash persistence await the One ROM's `onerom update commit` ("commit live image to flash", currently *not yet supported*). **HARDWARE-ONLY** to validate (the swap + RBCP are inert in VICE): flash-test that `font 1` then `basic` gives a Swedish keyboard, and confirm the $EB81/$EBC2 slot offsets are right (they assume the verified KERNAL-first slot layout). `test_rbcp` only checks the launcher still copies to RAM cleanly and the back-channel window stays free.

**JiffyDOS-style wedge aliases** (v0.1.68, `wedge_rewrite` in shell.c, CODE2): the line is rewritten in place between readline and parse -- `@` = `status`, `@$` = `dir`, `@#<n>` = `device <n>`, `/x` and `%x` = `load x` (load always honors the embedded address, so they coincide), `^x` = `run x` -- the load/run forms quote the whole rest of the line (v0.1.70), so `/my game` loads MY GAME like real JiffyDOS. Runs after history_add, so recall shows what was typed. Not aliased (falls to "Command not found"): raw `@<dos-cmd>` passthrough (would be a new feature -- the files overlay's `command_channel` is the natural home if wanted) and `<-file` save (no save command). Not in the dispatch table, so `help` doesn't list them. Tested in test_disk::test_wedge_aliases (`^` is hardware-only -- it swaps ROMs).

**The editor wraps long lines** (v0.2.06): a logical line longer than the window occupies as many display rows as it needs. BASIC lines run to 80 characters, so without it the right-hand half of a listing was invisible and the cursor stuck at column 39. `render_row` breaks a row at a CR *or* at `COLS`, and `row_next`/`row_start` give the display-row arithmetic that `render`, `ensure_visible` and the light repaint path now use instead of `line_start`. Cursor up/down still move by logical LINE, which is the right behaviour for this kind of editor.

Line editing landed: `readline` in `src/shell.c` tracks a cursor index (`pos`) and length (`len`). Cursor left/right ($9D/$1D) move within the line, printable characters insert at the cursor (pushing the tail right), and DELETE removes the character to the cursor's left and closes the gap. Append-at-end and delete-at-end keep a cheap fast path; mid-line edits call `redraw_line`, which steps back to the line start, reprints the whole line plus a trailing space (to wipe a just-deleted cell), and parks the cursor. CHROUT (`src/screen.s`) handles $1D/$9D by moving the cursor, wrapping across rows at column 0/39 (cursor-left at column 0 steps to the previous row's column 39, and vice versa) so a line that wraps to a second screen row edits correctly. DELETE ($14) wraps the same way: at column 0 it steps back to the previous row's column 39 before blanking, so backspacing across a wrap erases the right cell and moves the cursor (it used to stick at column 0 — dropping the char from the line buffer while leaving the screen unchanged). **HOME ($13) moves to the start of the input** (not the screen home) and **CLR ($93, shift-HOME) wipes the pending input** (not the whole screen) -- line-editor semantics, v0.1.57; programs printing $13/$93 through CHROUT still get the screen-level behavior, and the `clear` command still clears the screen. Tests that used to inject a CLR keystroke to reset the screen type the `clear` command instead (the keystroke is inert at an empty prompt). `test_lineedit.py` injects cursor codes and asserts the dispatched command (and `$D3`/`$D6` for the cursor column/row, including both the cursor-left and the DELETE wrap, HOME insertion at the front, and CLR wiping the line but not the screen).

Command history: `readline` keeps the last `HIST_N` (8) submitted non-empty lines in a ring buffer; cursor-up ($91) recalls older entries and cursor-down ($11) walks back toward the fresh line. A recalled line replaces the current one via `replace_line` (step to line start, draw the new text, pad over any leftover of a longer old line). `test_history.py` submits two commands, navigates ≤2 back, edits, and asserts the dispatched command.

Tab completion (of *command names*) was implemented and later **removed** (it was rarely useful and cost resident ROM). TAB ($09) is currently an inert keystroke in `readline`; CTRL+I still emits $09 for the `edit` overlay's bindings. *Filename* completion landed in v0.1.58 (`docs/TAB-COMPLETION.md` has the full rules): TAB -- **emitted by a bare CTRL tap** (`ctrl_tap` in irq.s; the C64 has no TAB key; CTRL+combos still work as modifiers) or CTRL+I -- completes drive filenames from the fixed $CE00-$CFFF name cache (two pages, ~40 names, 16-bit walk; names stored uppercase-folded -- network folders list lowercase PETSCII) that `ls`/`dir` fill as they draw (list first, then complete). $CF00 doubles as the run stub's home; launch_stock_program invalidates before planting. Unique match completes, ambiguity extends to the common prefix, a no-progress TAB lists candidates and reprints the line. **The opening quote goes in as soon as a spaced name is among the CANDIDATES** (`anysp`, `$03A3`), not merely when the common prefix itself contains a space -- quoting on the prefix alone broke as soon as a third name shortened it below the space, because typing the rest (` bb`) then began a NEW word and completion hunted for a name starting `bb` (hardware-reported, fixed v0.1.96; shifted space `$A0` counts too, being just as much a word break to the parser). **TAB on a fully-typed, unique name inside an open quote adds the CLOSING quote** (v0.1.97) even though there is nothing left to complete -- the parser treats an unclosed quote as running to EOL, so until it is closed no further argument can be typed (`cp "my game" dst`). Previously TAB there did nothing: the "no progress" path skipped the insert entirely. Watch the `kins == 0` case in the insert loop -- `dec jtmp` from 0 wraps and would copy 256 bytes, so the zero test must come first. The cache is invalidated by cd/device/rm/mv/cp/SAVE, a load overlapping $CE00, dir errors, and boot. **Names with spaces work end to end** (v0.1.70): the parser has always grouped `"quoted"` tokens (unclosed quote runs to EOL), completion is quote-aware (auto-inserts the opening quote when completing a spaced name from an unquoted word; closes it on a unique match), and the wedges quote their rest-of-line. Not handled: a name containing `"` itself. The matcher is hand-written assembly (`src/complete.s`, ~600 bytes in the BASIC half's CODE segment; it was ~1.3KB as cc65-compiled C first): readline passes length/cursor via $02B1/$02B2, state at $02B3-$02BB, zp walk pointers $FB-$FE. The CTRL-tap emission is matrix-driven (GUI/hardware-verified); the completion logic is fully tested by seeding $CE00 (test_lineedit).

Utility commands: `sys <addr>` (`cmd_sys` in `fs.c`, resident) calls machine code at `<addr>` in the **current (Tardis) environment**, as a subroutine -- it JSRs in via `run_program` (`c_io.s`; a purpose-built trampoline that had gone unused until `sys` revived it) and returns to the prompt when the routine RTSes. It is BASIC's `SYS` but WITHOUT the run/stock-ROM swap, so it suits routines that use only the **documented KERNAL entry points** ($FFD2 CHROUT, $FFE4 GETIN, the file-I/O vectors) or that merely trip an **I/O-region device** -- the motivating case is a **SIDKick pico** config trigger (`sys 54301` / `sys 54333` = `$D41D`/`$D43D`), which the SIDKick detects on the bus regardless of which ROMs are mapped. Anything that needs stock KERNAL/BASIC belongs on `run` (which swaps); a routine that never RTSes or trashes the stack takes the shell with it (reset to recover, exactly like `SYS`). It is **resident, not an overlay** (unlike peek/poke) so the SYS'd routine sees clean user RAM with no overlay parked at $8800; it carries its own tiny `parse_addr` (decimal by default, hex with a `$` prefix -- the peek/poke rule, so `sys 54301` matches the BASIC number). `test_sys.py` pokes a small `STA $D020;RTS` routine, `sys`es to it, and checks the write happened AND the shell came back. **Banks are multiple now (v0.1.95).** The bank ABI carries an identity so `bank_call` can verify it got the set it asked for: `$A000` = `"bnk"`, `$A003` = the **bank id**, `$A004+` = the JMP table. `bank_call` takes one byte -- bank id in the high 3 bits, entry in the low 5 (`BANK_CMD(bank, entry)` in `shell.h`) -- so a dispatch-table row stays 4 bytes whichever bank a command lives in, and `bank_flash_set[]` in launch.s maps id -> flash set (**0 = disk, set 8; 1 = util, set 9**). Checking the id (not just `"bnk"`) is what stops a mis-numbered flash set running one bank's entry table against another bank's code. **The util bank** (`cfg/util_bank.cfg`, `src/banks/crt0_util.s`) holds **tab completion** (`src/complete.s`, ~700 B out of the tight BASIC half). It is a separate image from the disk bank on purpose: its payload is pure asm with its state already in page 2, so it needs **no cc65 runtime -- no C stack, no DATA, no BSS -- and therefore takes nothing out of the program load area**, where the disk bank costs `$9D70-$9FFF`. Two pieces of plumbing were needed: **`line` is pinned at `$C000`** (its own `LINEBUF` segment in `cfg/rom.cfg`, bound to the same address in `cfg/util_bank.cfg`) because the matcher indexes it with absolute,X and ordinary BSS moves between builds; and **`_print_prompt` is reimplemented in the bank** from the `$02D1` device mailbox, because the resident one lives in the BASIC half -- *swapped out while a bank runs*, and an SVC entry cannot help since a JMP into the swapped-out half lands in the bank's own code. **Only KERNAL-half code is ever reachable from a bank; that is the hard rule the SVC table obeys.** With `_print_prompt` supplied under the name it already imports, `complete.s` moved with zero source edits (like `dir.c` and `fastload.c`). TAB is **silent** when no bank answers (`bank_try` vs `bank_dispatch`) -- a keystroke that quietly does nothing beats an error mid-line. Tests seed one bank at a time (`seed_util_bank`/`seed_disk_bank`), since all banks link to `$A000` exactly as the RAM overlays all share `$8800`.

**The EDIT BANK + BASIC listing (v0.2.01).** The editor **outgrew the RAM overlay region**: code+rodata reached 5783 bytes against the 5376 that fit between `$8800` and the bank RAM, and adding the BASIC detokenizer put it past what `$8800-$9FFF` can hold at all once its BSS (177 B) and C stack are counted. It is a bank now (`src/banks/edit.c`, `crt0_edit.s`, `cfg/edit_bank.cfg`, bank id 3) with ~2.3KB spare for the tokenizer later; its **document buffer is unaffected** -- that was always `$0800` in user RAM. It reads its own filename from the published argv, so `edit` is a pure dispatch row with no resident thunk (`cmd_edit` and the last `mp_fetch` caller but `about` are gone). The edit bank took the flash slot the **second overlay set vacated** (set 5), so nothing else renumbered -- but note a bank set is **[kernal | charset | bank image]** while an overlay set is the *same image on all three chips*, so the slot must be rebuilt from another BANK set, never edited in place. Getting that wrong served the editor as the character ROM (the screen filled with giant garbage glyphs) and as the KERNAL; nothing in the build or the suite noticed, since every image was valid and merely wired to the wrong chip. `test_rbcp::test_bank_flash_sets_have_the_right_chip_layout` now checks the shape of every bank set -- `about` is the only RAM overlay left, alone in set 4. The shared bank BSS window widened to `$9D10-$9E0F` (256 B) to fit the editor's 177; the C stack is ~500 B and the `$9D00` floor (and so the load ceiling) is unchanged.

**BASIC display (stage 1 of a tokenizer):** `edit <prog>` on a tokenized BASIC program now shows it as a **listing** instead of failing to open. Three pieces: the editor opens **by name only** (its old `",s,r"` restricted it to SEQ, so a PRG reported as missing); a file whose load address is `$0801` *and* whose first line link points forward past it is treated as BASIC (the address alone also matches data that happens to start `$01,$08`); and the expander walks link/line#/tokens, with its **own ~280-byte keyword table** -- the stock BASIC ROM is precisely what this shell replaced, so there is nothing to borrow at runtime. Raw bytes are staged at `BUF+$5000` and the listing expands *down* from 0, since text is 2-3x the size of the tokens. **Bytes inside quotes are passed through untouched** (BASIC does not tokenize inside strings). **Saving tokenizes it back** (v0.2.04): the listing goes out as a PRG with its `$0801` load address, built in the gap buffer's free middle (tokenized output is always smaller than the text, and `chat()` never reads the gap, so the document stays readable while it builds). Keyword matching is **first-match in table order**, which is why the table's order matters -- `INPUT#` precedes `INPUT`, `PRINT#` precedes `PRINT`. Input is uppercase-folded while matching, so a listing typed in the shell's lowercase tokenizes the same. **Tokenizing is suspended inside quotes, after REM (to end of line) and after DATA (to the next colon)** -- exactly as BASIC's own CRUNCH does. That last rule is not optional: without it "DONE" stores as `D,<ON>,E`, which changes the bytes of a program that merely round-trips and breaks what READ returns from a DATA item (found by the byte-exact test, not by reading the listing -- it *looked* right). Lines must be in ascending order (the link chain assumes it); out of order is refused with "lines out of order" rather than writing a program that lists wrongly. `test_edit::test_edit_basic_roundtrip_is_byte_exact` loads, saves, `load`s the result back and compares the bytes in memory against an independently-constructed image; the fixture carries a keyword in a string, in DATA and in REM. `test_edit::test_edit_lists_a_basic_program` covers all of it against a genuinely tokenized fixture (`bas` on `test/data/test.d64`, carrying a keyword inside a string to prove quotes are respected).

**`debug` -- the live keyboard-matrix viewer (v0.2.11, `src/banks/kbdiag.s`, util bank entry 2):** draws the raw CIA bits as an 8x8 grid (plus each select line's byte in hex), refreshed as fast as the CPU can scan, RUN/STOP to quit. It sits BELOW the decode tables, the debounce and the repeat logic on purpose -- what it shows is the hardware and nothing else. Pure asm in the util bank, so it costs the 16KB ROM one dispatch row and the load area nothing. **Why it exists:** a real machine lost all eight keys on ONE select line (PA4: 9 I J 0 M K O N) with every other line fine, and no amount of code reading could distinguish that from a scan bug -- the keys just produce nothing and the tables look correct because they ARE correct. Two software theories died on the way: a **settle delay** (our scan read `$DC01` immediately after selecting on `$DC00`, where the stock KERNAL's loop happens to leave 5 cycles) made no difference on hardware, and stock's apparent "N repeats when held" was never repeat at all -- stock only auto-repeats cursor/space/DEL, so a repeating N is a contact making and breaking, i.e. the fault itself. The settle fix was kept anyway because the test written to pin it (**every `$DC00` select must be followed by a real gap before the `$DC01` read**) found two genuine latent bugs: `nmi_stub` and `rbcp_nmi_escape` both read back-to-back, where a missed read silently swallows RUN/STOP+RESTORE. `reset.s`'s boot C= check had had an 80-cycle settle all along -- the lesson had been learned once on one path and never generalised. Note our repeat applies to ALL keys (stock's does not), so "every key repeats when held" is this shell working as designed, not a symptom. `test_kbdiag.py` is its own module: the viewer runs with interrupts off and exits only on a physical RUN/STOP, which the harness cannot press, so it parks the machine like `test_parse_addr` does; it asserts all eight lines render open ($FF) with nothing held, which catches a transposed grid, a wrong address, a reversed bit walk or a broken hex nibble.

**THE RAM OVERLAYS ARE GONE (v0.2.09).** `about` -- the last one -- moved into the **util bank** (entry 1), which was 90% empty and, like `about`, needs no cc65 runtime. With it went the entire mechanism: `src/commands/overlay.c` (`mp_fetch`/`mp_cached`/`mp_failed` + the retry loop), `overlay.h`, `tools/gen_overlay_pages.py`, `build/overlay_pages.h`, every `cfg/overlay_*.cfg`, the whole `src/overlays/` tree and the overlay flash sets. **basic 3741 -> 4107** free. One command now reaches its code exactly one way. **`bank_gosub` no longer clears `$8803`**: that invalidation existed because a bank's RAM init overwrote the tail of a cached overlay while the cache was validated only by that magic (the v0.1.90 `cd` failure) -- with no overlays it is not merely redundant but HARMFUL, since `$8803` is ordinary user RAM again and zeroing it after every disk command would corrupt a loaded program. **Flash sets renumbered** (the overlay set left a hole): C64 = 0 bootloader, 1 Tardis, 2 stock, 3 JiffyDOS, **4 edit, 5 font B, 6 disk, 7 util, 8 files, 9 hex**; C128/C64C = 0 Tardis, 1 edit, 2 disk, 3 util, 4 files, 5 hex, 6 stock. `FONTB_FLASH_SET` (fs.c) and `bank_flash_set` (launch.s) are the two places that encode this. The C64C/C128 scripts were ALSO still listing the deleted `overlays_b` and had never been given the edit or hex banks -- so those commands would have been unreachable there; fixed in the same pass.

**The HEX EDITOR bank (v0.2.08)**, `hex <name>`: a byte editor -- address column, hex pane, PETSCII pane, overwrite-only (a hex editor must not change a file's length). `src/banks/hex.c` + `crt0_hex.s` + `cfg/hex_bank.cfg`, bank id 4, flash set 10 (**appended, so nothing renumbered**). It opens **by name only**, so it gets PRG or SEQ alike and a PRG's load address shows as the data it is. **Whole-file into `$0800` user RAM**, not a paged window over the file: a CBM drive has no cheap seek (sequential files read start-to-end; random access needs REL files or U1/U2 block commands that network drives generally lack), so a paged design would re-read from the start on every scroll -- RAM is the resource we actually have. Written against our own primitives rather than ported, it needs no screen or printf library and lands at **3438 bytes, 41% of its window**.

**Shared PETSCII rendering (svc 12, `scr_display` in `src/screen.s`):** screen code for ANY byte, adding the reverse-video quote-mode rule for control codes (`$00-$1F` -> code `c`; `$80-$9F` -> `(c & $1F) + $40`) on top of `pet2scr`'s printable and graphics ranges. It lives in the KERNAL half, which stays mapped while a bank runs, so every bank reaches it through the SVC table. The text editor used to carry a 96-byte runtime table plus three helpers for this and the hex editor would have been a third copy; folding it here took the edit bank 7840 -> **7596** bytes and returned **96 bytes to the shared bank RAM window**.

**The FILES BANK (v0.1.96)** retired the two biggest RAM overlays. `files.c` (cat/less/cp/mv/rm/status/cd/border/bg/text/peek/poke/help/device/devices) **and `picker.c`** moved to `src/banks/`, served as ROM at `$A000` (bank id 2, flash set 9). The picker had to come along: `border`/`bg`/`text` with no value open it, and **a bank cannot fetch a RAM overlay** -- the fetch machinery is resident BASIC-half code, swapped out while a bank runs. `src/banks/files_entry.c` is the entry layer (one entry per command: argc check, argv -> the same `$02D0` mailbox files.c always read, usage strings, the `cd` command builder), so `files.c` itself moved essentially unchanged. With data-driven dispatch these commands now cost the 16KB ROM **nothing but a 4-byte row and a name**: `files_run`, every cat/less/cp/mv/rm/cd/status/device/devices thunk, all of `config.c` and `mem.c`, the resident `cmd_help`, and `run_files_overlay`/`run_picker` are gone. **basic 1817 -> 3596, kernal 2101 -> 1908** (net +1586; ~5.5KB free total). **Banks share one RAM window** (`$9D70-$9FFF`): only one is served at a time and each re-inits its own RAM per entry, so adding banks costs no further program space and `$9D6F` stays the load ceiling. Only `edit` and `about` are still RAM overlays, so the overlay sets dropped to two (A=edit, B=about) and the loadable sets renumbered -- **banks are 7 disk / 8 util / 9 files** (`bank_flash_set` in launch.s). **The subtle bug worth remembering:** `help` printed structured garbage because the dispatch table is in `RODATA2` (KERNAL half) but its **name strings were in `RODATA` (BASIC half)** -- a bank following those pointers reads its own code. `shell.c` now pushes `rodata-name` to `RODATA2` for the whole file and never pops (cc65 emits the literal pool at end-of-unit using whatever is current there). **The rule is about DATA a bank follows, not just code it calls: only the KERNAL half is reachable.** Tests seed one bank at a time (`seed_files`/`seed_disk_bank`/`seed_util_bank`), so a test crossing banks must re-seed.

**Data-driven dispatch (v0.1.92):** a dispatch-table row can name a **bank entry** instead of a resident function -- `{ "ls", BANK_CMD(1) }` -- so a bank command has **no resident code at all, only its 4-byte row plus its name**. `BANK_CMD(n)` (`shell.h`) stores the entry index in the handler slot; real code never lives in page zero, so a handler below `$0100` is unambiguously an index (`IS_BANK_CMD`). `dispatch()` routes those through one shared `bank_dispatch()` (`fs.c`), which publishes the default device + its remembered name (resident, since the prompt and every disk command read them) and **argc/argv at `$03A0`** -- so the bank parses its own arguments and prints its own errors. **Adding a bank command therefore costs ~0 resident bytes**, which is the answer to "new functionality keeps filling the 16KB"; converting the five existing ones (dir/ls/pwd/fload/load) freed **745 bytes** (basic 955->1131, kernal 1563->2132) by deleting `dir_run`, the dir thunks, `cmd_load`, `cmd_fload`, `fload_program`, `fold_name`, and the resident `print_hex16`/`report_no_device`/`report_drive_status` they kept alive. `run` stays resident (it drives the stock swap) and calls entry 3 for its fast load. **The NAME deliberately stays resident**: it keeps `help` a single sorted list, and it keeps "Command not found" honest -- with no One ROM, `ls` reports *disk bank unavailable* (true) rather than *not found* (false); `test_shell::test_bank_command_is_known_not_unknown` pins that.

**`load_start`/`load_end` ARE the disk-bank mailbox cells** (`$039A`/`$039C`), not resident copies: both loaders run in the bank, so the bank is what learns the addresses. They were copies until v0.2.00, and when data-driven dispatch deleted the resident load/fload thunks only `run <name>` still copied -- so `fload x` then a bare `run` said "nothing loaded" and `load x` then `basic` cold-swapped instead of handing the program over (hardware-reported). `reset.s` zeroes them at boot (page 3 is power-on garbage; a nonzero `load_start` would make a bare `run` launch nonsense), and the bank invalidates the `$CE00` completion cache itself when a load lands across it. `test_run::test_load_then_bare_run_finds_the_program` covers the sequence.

**`load` is a disk-bank command too** (entry 4, v0.1.91), with `report_drive_status` -- which has to be in the bank, since reporting the drive's own reason means reading its error channel before the resident side regains control. **Max loadable program end is `$9CFF`** (v0.1.99; page-aligned so the fast-load guard is exact): the bank's DATA/BSS/C-stack occupy `$9C00-$9FFF`, and since `load`/`fload` now run FROM the bank, a program growing into that would overwrite the live C stack *mid-transfer* -- a crash, not a survivable clobber (when `load` was resident a big load hit only the dir overlay, which self-heals because overwriting its magic forces a re-fetch). The bank's RAM is packed high and contiguous (`$9D70-$9FFF`: DATA, BSS, then a 512-byte C stack) and `load` refuses at the boundary with "program too large" instead of crashing. **The Epyx descramble table is assembled into the bank's ROM** (`src/fastload_recv.s`, a `.repeat` over the permutation) rather than generated into BSS at run time: the old trade -- ~226 ROM bytes saved by building a 256-byte table in RAM -- was right when that code was resident in the 16KB image and is wrong in a bank, where ROM is spare but every RAM byte comes off the largest loadable program. That move alone raised the ceiling by 368 bytes, grew the C stack from 410 to 512, and dropped the per-entry rebuild (a bank re-inits on EVERY entry, so it was rebuilding the same 256 bytes before every disk command). The assembled table is verified byte-identical to both the formula and a bit-for-bit simulation of the deleted generator; **`fload` is guarded too** (v0.1.99): its timed receiver cannot afford a per-byte compare, so the test rides the destination's PAGE CROSSING (`BANKPG` in `fastload_recv.s`) -- free on 255 of every 256 bytes, and exact because the bank RAM window is page-aligned for that reason. It reports "program too large" (`$03A4`), not "fast load failed", so the user isn't sent hunting a bus problem. `test_rbcp::test_bank_ram_ceiling_and_loader_guards_agree` checks the window start, `BANKPG` and `BANK_RAM_FLOOR` all agree -- the realistic rot is moving the bank RAM and forgetting a guard. `parse_addr` (`src/parse_addr.s`, used by `sys`) is **assembly**: cc65 compiled the same ~20 lines of C into 251 bytes (the 16-bit shifts and the x10). It was NOT moved to a bank on purpose -- `sys` is resident precisely so the routine it calls sees user RAM the shell hasn't disturbed, and a bank call writes over `$9C00-$9FFF`. `test_parse_addr.py` exercises it directly (its own module: calling it with `run_at` parks the CPU). Also: `hist[][]` rows are **64** and `device_name[][]` rows **16** -- powers of two, so indexing is a shift; the old 81- and 11-byte rows made cc65 emit 16-bit multiplies that dragged `mul.o`+`mul8.o` (~127 B) into the ROM. The files overlay's `DEVNAME_STRIDE` must track `DEVNAME_ROW`.

`peek <addr> [count]` / `poke <addr> <val>` (`src/commands/mem.c`, `parse_num`: **decimal by default, hex when prefixed with `$`** -- the C64 convention, so `poke 53280 0` works for anyone with BASIC muscle memory and `poke $d020 0` is the same register; a bare hex-looking value is read as the decimal the user meant, not silently as hex) read/write live memory -- `peek` with a count hexdumps a range (8 bytes/row with address labels, for reading a loaded program's bytes); `device <n> [name]` (`fs.c`) sets the default IEC unit that the disk commands use (a `default_device`, boots as 8) — but it **probes the bus first** (`device_present` opens the unit's "$" and checks for the no-device timeout): if `<n>` doesn't answer it prints "device `<n>` not present" and *keeps the current device*, so a typo'd unit can't silently misdirect later commands. The tradeoff: you can't pre-assign or name a unit whose drive is powered off (the probe rejects it). An optional name, given for a present unit, is remembered per device number (`device_name[8..15]`) and reused when `device <n>` is given later without one; **with neither a name arg nor a remembered name, `device <n>` fetches the drive's identity** (v0.1.61: `fetch_identity` in the files overlay sends "UI" -- the quick warm reset -- and reads the channel-15 73-message; a model number in the text wins ("1541"/"1571"/"1581"), else the first word lowercased: "meatloaf", "sd2iec") into the name slot. **The prompt shows "8: meatloaf>"** -- the unit number, then `: <name>` when a name is set (`print_device_prefix`, format settled v0.1.62). **The boot path identifies the default device automatically** (`identify_boot_device` in main -> files overlay cmd 17, quiet: prints nothing, swallows a failed overlay fetch, and runs the bus in probe mode). `dev` is a dispatch-table alias for `device`. **`devices` (files overlay cmd 18)** scans units 8-15, prints each present drive's full identity line ("8: MEATLOAF CBM 20260629.19"), and fills empty name slots as it goes. Scans use **IEC probe mode** (`PROBEF` $02BC, cleared at boot): it bounds iec_sendbyte's normally-unbounded waits -- the ready-wait (~0.7s), and since v0.1.73 also the EOI handshake (`hs_eoiack`/`hs_eoirel`) and the data-byte ack (`hs_ack`), which were the holes that let a sick Meatloaf (acks the LISTEN, never services the EOI ack of a command's final byte) wedge the boot-time identity fetch forever (hardware-diagnosed 2026-07-14; the wedge point was the `"ui"` command's EOI byte) -- so absent/booting/wedged units time out; the AUTOEXEC-class hazard (VICE's empty drive holds DATA low on OPEN); never set it for normal transfers (a busy drive would be falsely dropped). `device <n>`'s presence probe and identity fetch run in probe mode too (v0.1.74), so a sick drive can't hang the shell interactively either -- a false timeout just reports "not present" / leaves the name slot empty. Probe mode + the quiet boot path are the groundwork AUTOEXEC needs if it's ever resumed. Hardware-verify: whether Meatloaf's UI warm reset preserves its network CWD (source read says yes); `reset` (`builtins.c`) reboots via `soft_reset` in `c_io.s` (`jmp ($FFFC)`); **RUN/STOP + RESTORE** is the keyboard shortcut for the same soft reset -- RESTORE is wired to the NMI line, so `nmi_stub` (`irq.s`) checks whether RUN/STOP (matrix col 7/row 7) is also held and `jmp ($FFFC)`s if so (RESTORE alone is ignored). Matrix-driven, so GUI/hardware-verified like the rest of the key matrix. `test_util.py` covers peek/poke/reset; `test_device.py` (drive attached, since the probe needs a real device to answer) covers `device` — absent unit reports+stays-put and a present unit names+recalls. The disk commands' own no-device path now reports the unit number too (`report_no_device`).

`status` reads the drive command/error channel (15) -- the "blinking red light" check. A thin resident thunk (`fs.c`, cmd 6) defers to the files overlay's `status_read` (the buffering + comma-field parse cost too much resident ROM): it opens channel 15 with no filename, buffers the raw `code,message,track,sector` reply **skipping the drive's own CR** (some drives -- Meatloaf -- end on the last data byte with no trailing CR, which is why the first naive version printed no newline and leaked a stray CR onto the next call), then reformats to `<code> <message>` (e.g. `00 OK`, `62 FILE NOT FOUND`), appending `@ track,sector` only on a real disk error, and always ends with exactly one newline. `test_status.py` checks the readable format, the error channel, and the fresh-line contract (the no-CR Meatloaf path is hardware-only -- VICE's 1541 sends the CR).

**The disk bank (`dir`/`ls`/`pwd`/`fload`/`run`'s fast path + the Epyx protocol), v0.1.88:** a **bank** is the second way to get code out of the 16KB ROM, alongside the RAM overlays. Where an overlay is fetched into RAM at `$8800`, a bank is an 8KB image the One ROM **serves at `$A000` in place of the ROM's own BASIC half** (`SWITCH_SLOT` to flash **set 8** = `[kernal | char | disk_bank]`, whose KERNAL+char are byte-identical to the base, so the swap is live-safe exactly like `font`). It runs from ROM, so it never clobbers user RAM the way an overlay at `$8800` does. `bank_call(entry)` (`src/rbcp/launch.s`, KCODE — it must live in the static KERNAL half, since the BASIC half is swapped out under it) does the swap and JSRs the bank's `$A000` JMP table (0 dir, 1 ls, 2 pwd, 3 fload); `fs.c` keeps only thunks. **While a bank runs the entire resident BASIC half is gone**, so the bank calls only the KERNAL stubs (`$FFD2` etc.) and the SVC table (`$FF80`) — which is why those exist at fixed addresses. Sources in `src/banks/` (`crt0_disk.s`, `disk_bank.c`, `dir.c`, `bank_svc_alias.s`), linked by `cfg/disk_bank.cfg`: code+rodata at `$A000`, and because that is ROM, all writable state goes to the `$98xx-$9Fxx` RAM the overlays used to run from (DATA `load=ROM run=$9800`, BSS `$9D00`, C stack at `$A000` growing down, zp `$40-$5F`). **This freed 1218 bytes** (basic 253→301, kernal 518→1688): the Epyx protocol, `fastload.c` + its M-W/M-E install payload, the resident fast path, the SVC Epyx entries, and reset.s's boot-time descramble generator all left the 16KB. Four things to know: (1) **`dir.c` and `fastload.c` moved with NO source edits** — `bank_svc_alias.s` aliases their Epyx `svc_*` names onto the bank's own local copies (pure symbol aliases: zero bytes, and a direct `jsr`, which the cycle-counted receive path needs), and `cfg/disk_bank.cfg` binds their `iec_*` names to the resident SVC slots; the shared asm (`fastload_recv/send.s`, `iec_clkwait.s`) is assembled a second time with `-D BANK_BUILD=1`, which only redirects its segment. (2) **Banks ARE VICE-testable**, which is not obvious for served ROM: the C64 has RAM *under* the `$A000` ROM that the shell never uses and that always receives writes, so `bank_call` falls back to running the bank from there (LORAM off) when no One ROM answers, guarded by a `"dsk1"` magic at `$A00C` so garbage RAM reports "disk bank unavailable" rather than executing — `seed_disk_bank()` (`test/lib/overlays.py`) seeds it like any overlay, and the suite kept **all 143 tests**. The magic also catches a mis-numbered flash set (the overlays' old "stage 5" failure). (3) **Bank RAM is not the bank's between calls**, so `bank_init` re-runs `zerobss` + `copydata` + the descramble-table rebuild on every entry (the resident build built that table once at boot). (4) The SVC table lost its 7 Epyx entries and gained `iec_set_fnadr`/`set_fnlen`/`command_raw` (svc 9-11) for `fastload.c`; it is now 12 entries, `$FF80-$FFA3`. **HARDWARE-VALIDATE the served path** (VICE only exercises the RAM fallback): `dir`, `ls`, `pwd`, `fload <name>`, `run <name>`. **v0.1.88 mostly worked on hardware but hung intermittently** (no pattern); the diagnosis is that the swap-BACK is the one step that must not fail -- a failed swap-in is recoverable, but returning into a shell whose BASIC half is still the bank means the NEXT resident call runs garbage, so the hang lands on a later command than the one that glitched. v0.1.89 adds `bank_ensure_base`: it does NOT trust the protocol's status (that report is the thing that glitches) but reads the truth -- if `$A000` still answers `"dsk1"` the bank is served, whatever was reported -- then retries the SWITCH up to 8 times and, failing that, `jmp ($FFFC)` so the boot slot-normalize gives a visible reboot instead of a dead machine. It runs on every exit path including the reported-failure one (a glitched response can mean the device switched anyway, which would otherwise run the RAM fallback with the bank underneath it), and costs nothing on the no-One-ROM path since the base's `$A000` never matches the magic. **The v0.1.88/89 hangs were actually a RAM collision, fixed in v0.1.90:** the bank's per-entry init writes `$9800-$9FFF` (DATA/BSS/C stack), which is the **tail of every RAM overlay** -- files' last 7 code pages (it spans `$8800-$9EFF`) and its BSS at `$9F00`, edit's upper pages and BSS, picker's BSS at `$9D00` -- but `mp_cached` validates the cache **only by the magic at `$8803`**, which sits below `$9800` and therefore survives, so the next overlay command called into a cache whose upper third was rubble. The tell was that `cd` failed most of the time while `bg`/`border`/`text`/`help` -- the *same* overlay, but lower in it -- worked, and `edit` always worked because its different magic forced a re-fetch anyway. `bank_gosub` now clears the magic after every bank call, so the next overlay command re-fetches (`test_disk::test_bank_call_invalidates_the_overlay_cache` pins it; verified to fail without the fix). The reverse direction was already safe -- an overlay clobbers the bank's RAM just as thoroughly, which is exactly why `bank_init` re-runs zerobss+copydata+descramble on every entry. Cost: one overlay re-fetch after each disk command. Collision-free placement isn't available (overlays occupy `$8800-$9FFF` and `$C000-$CFFF` is spoken for), so invalidation is the honest fix.

The "files" overlay is now the general home for movable command bodies -- mailbox cmd ids: 0 cat, 1 less, 2 cp, 3 mv, 4 rm, 6 status, 7 cd, 8 border, 9 bg, 10 text, 12 peek, 13 poke, 15 help, 16 device (5 was save, 11 was prompt, 14 was echo; all removed). New commands should default to joining it (a thin resident thunk + a cmd id) rather than growing the 16KB ROM. **Now resident only:** `ver`/`clear`/`reset` (tiny/cold, a thunk would cost as much), `basic` (drives the ROM swap), and `load`/`fload`/`run` (the IEC/Epyx + ROM-swap path). Notes on the trickier moves: **peek/poke** (cmds 12/13, mem.c thunks) -- the overlay does the number parse + memory access + hexdump, but it clobbers zero page as it runs, so overlay peek/poke can't reliably touch ZP (fine for I/O regs + user RAM). **help** (15) -- the thunk passes the dispatch-table base ($02E4) + count ($02E6); the overlay walks the `const struct command[]` (4-byte entries, name ptr at +0) and does the 3-column layout. **device** (16) -- `default_device` + `device_name[8][11]` STAY resident (read by every disk command + `current_device_name` for pwd); the thunk passes their addresses ($02F4/$02F6) so the overlay updates them in place, and probes the unit via the KERNAL OPEN shim (`device_present_ov`). `files_run` is exported (shared by fs.c + mem.c thunks). The original file commands: `cat`, `less`, `cp`, `mv`, and `rm`. Their bodies are a multi-page C overlay (`src/overlays/files.c`, magic `fil1`, built with `crt0_files.s` + `cfg/overlay_files.cfg`, runs at $8800 like `edit`); the resident side is just thunks in `fs.c` that fill a mailbox at `$02D0` (command id, device, two length-prefixed args) and call `run_files_overlay` (`overlay.c`), which fetches the overlay on demand and validates its header magic. **The RBCP transport used to glitch intermittently on real hardware** (a fetch could fail at enter/stage 1, peek/stage 3, or come back with corrupt data/stage 5 = bad magic). Root cause (v0.1.56): RBCP commands are *reads* of the $E0xx command page, and a VIC-II badline stalls the CPU mid-read, re-presenting the same address for several ph2 cycles -- the device counts the duplicates as extra protocol bytes and the frame shifts (a corrupted SLOT_PEEK offset even "succeeds" into the wrong page = the stage-5 bad magic). The boot-path swap never glitched because the display is blanked there (no badlines). Fixed by `rbcp_vic_guard` (launch.s, called from `rbcp_knock`/`rbcp_send_cmd`): each command frame waits for a raster window with >= 5 badline-free lines, the same pacing trick as the Epyx receiver; it assumes YSCROLL=3 and no sprites. `overlay.c` still retries the whole fetch up to `OVL_RETRIES` (2 since v0.1.66; hardware confirmed fetches stopped failing post-guard) times as a safety net -- each attempt restarts with `rbcp_reset`, which flushes device state; the protocol's own retry only covers the command-token poll, not progress/response/data. **`overlay.c` lives in the default CODE/RODATA (BASIC ROM half), not CODE2** -- the retry loops grew CODE2 into the reserved `$FE00` back-channel window (`test_rbcp::test_back_channel_window_is_free_fill` catches this); the cross-bank calls to the launch.s fetch trampolines are fine since both halves are always mapped. The overlay reaches the drive only through the fixed KERNAL entry points (SETNAM/SETLFS/OPEN/CHKIN/CHKOUT/CHRIN/CHROUT/CLOSE/CLRCHN) -- same ABI `edit` uses; `cp`'s write relies on the deferred-write CHROUT (last byte flushed with EOI on CLRCHN) and `mv`/`rm` send their command by OPENing secondary 15 with the command string. **Overlay page numbers are generated, not hardcoded:** `tools/gen_overlay_pages.py` derives each overlay's start page + flash set from the actual `.bin` sizes into `build/overlay_pages.h`, which the resident thunks `#include`. Current `LAYOUT` (three sets since v0.1.63): **set A** (loadable set 2) = `files` alone (23 pages -- the growing overlay gets the headroom; its link area is OVL $1700 with a 1-page OVLBSS at $9F00, extendable to $1800 by moving the 1-byte BSS); **set B** = `edit` (19 pages); **set C** = `about`, `picker` (dir left set C when it became the disk bank, below). (`dir` used to share set B with `edit` -- 32 pages, exactly full -- but that left 0 spare pages, so when `pwd` gained the `PWD`-command path `dir` moved to set C, which has headroom. `dir` is back to 13 pages now that `pwd` drops its old device/name prefix, but it stays in the roomier set C.) `devices` prints a progress dot per probed unit and DEL-wipes them when an entry prints (and at the end). The big overlays (`files` 22, `edit` 19) must live in different 32-page chips, and files+dir (22+13) no longer pair, which forced this packing (the only one that fits). The files overlay's own link area also grew (`cfg/overlay_files.cfg`: OVL $1600, OVLBSS at $9E00). The Makefile `OVERLAYS_A`/`OVERLAYS_B` concatenation order MUST match the per-set order in `LAYOUT`. **Build gotcha (fixed):** the set membership/order lives only in the Makefile, so regrouping (e.g. moving `about` between sets) doesn't touch the member `.bin`s -- make would then see the stale `overlays_a.bin` as newer than its prereqs and skip the rebuild, baking the *old* page layout into the firmware while the resident macros use the new one (mismatch -> every set-A command fails `stage 5`). It moved from a single 256-byte page to multi-page in set B (with `edit`) when the text outgrew one page; `cmd_about` fetches it with `mp_fetch` like the C overlays. **Persistent settings (colors + history + font) in the One ROM NV flash:** the three colors (border/bg/text), the command history, and the selected font (font A/B, which also drives the Swedish keyboard layout) survive a power cycle, stored in the One ROM's non-volatile flash via RBCP group $03. (The blob still carries the version-3 length-prefixed prompt field at offset 7, but it's vestigial now -- always ">", written but not applied -- kept only so already-saved blobs still load without a format/version change.) `src/rbcp/rbcp.s` gains the poke-transaction wrappers (`nv_poke_begin`/`nv_poke`/`nv_poke_commit`/`_discard`) over the existing `get_nv_capability`/`nv_peek`; `src/rbcp/launch.s` adds C-callable `_nv_capability`/`_nv_read`/`_nv_write` (same copy-to-RAM + CR-mode + SEI trampoline discipline as the overlay fetch -- **the entry points must be `.segment "KCODE"` (run from ROM, call `copy_to_ram` first) and only the trampolines `.segment "RBCP_CODE"` (run from RAM); putting an entry point in RBCP_CODE makes C call uninitialized RAM and hang the boot**). To avoid a flash of the default brown, `reset.s`'s `restore_colors` reads just the 6-byte header (magic+version+3 colors) from NV and applies border/bg/text **before the display is enabled** (then re-`sei`s, since the NV trampolines `cli`); the C `settings_load()` later re-applies the same values harmlessly. **Watch the KERNAL ROM budget:** the NV code lives in the KERNAL half, and growing it pushed the segments into the reserved RBCP back-channel window at $FE00 (`test_rbcp::test_back_channel_window_is_free_fill` caught it) -- keep cold C settings code (e.g. `settings_save`) in the BASIC half (the default `CODE` segment), not `CODE2`. The C side is in `shell.c`: `settings_load()` (top of `main()`) probes capability -- **gating everything on NV being present + writable, so on VICE / a non-host-control build the handshake times out and persistence is inert** -- then applies the colors, re-applies the saved font via `font_select()` (fs.c -- re-runs the RBCP charset swap + Swedish key tables at boot, since the One ROM always powers up serving font A), and replays history through `history_add`; `settings_save()` builds a compact blob (`"TD"` magic + version + 3 colors + **font byte** + **length-prefixed prompt** + hist_count + length-prefixed history, oldest-first, entries capped at 22 chars, ≤208 B) and writes it. The header is **version 3** (offsets 0-6 = magic/version/3 colors/font are fixed; a length-prefixed prompt at offset 7 -- now vestigial, see above -- then shifts hist_count + history); `reset.s`'s `restore_colors` (which only reads the fixed offsets 0-5) checks for `$03`. To bound flash wear it saves only on a color change or every 8 commands (and on `basic`, via `cmd_basic`, and immediately on a `font` change so the choice can't be lost before the next command), never per-command -- plus, since v0.1.65, an **idle checkpoint**: once the prompt sits ~5s idle with unsaved commands (readline's empty-poll drives `settings_idle`, jiffy-clocked), it saves once -- one write per typing pause, catching short sessions that never reach the 8-command mark; `reset` also saves before rebooting. Note **reflashing the One ROM firmware wipes the NV area** (the image rewrite takes the plugin's NV region with it) -- settings loss after a flash is expected, not a bug. (An `nv` diagnostics command existed v0.1.64-v0.1.68 for the "history doesn't persist" investigation; verdict: persistence worked all along -- reflashing wipes the NV area and short sessions missed the old 8-command-only cadence -- so it was removed in v0.1.69 once the idle checkpoint settled the cadence. The write is ~150 per-byte RBCP pokes + a flash commit, badline-guarded like all sends.) The blob lives in a `shell.c` static (BSS, $C000-$C7FF, clear of the $C800 RBCP copy); a page-2 mailbox ($02C4-$02C7) passes the buffer address + length to the trampolines. Hardware-only like the rest of RBCP (VICE has no NV); the round-trip is hardware-validated (2026-07-02: history survives power cycles).

**Deferred — AUTOEXEC:** running commands from an AUTOEXEC file at boot is *not* done. The blocker: doing IEC at boot hangs when the drive isn't cooperating. `iec_sendbyte`'s `@wlisten` now times out (see Phase 6 below), so an *absent* device no longer wedges the send — but VICE's empty drive (no disk) *holds DATA low* when sent an OPEN, so `@wlisten` (which waits for DATA low) passes immediately and the boot can still wedge at the still-unbounded `@wready`/`@ack` waits (and a real 1541 isn't ready for ~1-2s after power-on). Fully unblocking AUTOEXEC needs a drive-ready wait (and/or timeouts on `@wready`/`@ack`) before the OPEN. The status-channel gate idea (read channel 15, proceed only on "00") is sound but can't run until the send can't hang.

Cursor and colors: the boot defaults (set in `reset.s`) are **border brown ($09), background orange ($08), text white ($01)** -- overridden by saved colors from NV if present (`test_memory.py` checks the brown/orange defaults). The cursor is a **static** (non-blinking) block: CHROUT clears the reverse-video bit (bit 7) of the cell it's leaving and sets it on the cell it lands on, so the cursor cell is always shown reversed — white block, with any character under it in the orange background colour. No timer/IRQ is involved. `screen_text()` masks bit 7, so the block is invisible to text assertions; `test_cursor.py` reads screen codes / colour RAM directly to check it's a static block and white.

SHIFT support: `scan_keyboard` in `src/irq.s` detects either shift key (`SHFLAG`) and, when held, decodes the found key through a second table `keytab_shift` instead of `keytab`. That table holds the **C64-native** shifted layout: letters fold to uppercase, the number row gives `! " # $ % & ' ( )` (shift-0 stays `0`), the punctuation keys give `< > ? [ ]` (shift-`,` `.` `/` `:` `;`), cursor-right/down become cursor-left/up ($9D/$91), and HOME becomes CLR ($93). Native (not a modern remap) is deliberate: VICE's default *symbolic* keyboard mapping translates a host symbol to the C64 key+shift that natively produces it (host `!` arrives as shift-1, host `&` as shift-6), so the table must decode those back to the same symbol; symbols the C64 makes with a dedicated key (`@ * +`, and the up-arrow for `^`) come through unshifted in `keytab`. One symbol needs the CBM (Commodore) key: VICE maps host `_` to the C64 `@` key + CBM (its only CBM-combined mapping), so `scan_keyboard` also tracks the CBM key — `SHFLAG` is a bitmask now (bit0 shift, bit1 cbm, bit2 ctrl, matching the KERNAL's $028D) — and decodes `@`+CBM to underscore ($5F). **CTRL is a modifier** (not a TAB key as in earlier phases): CTRL+letter emits the ASCII control code ($01-$1A, so ^X=$18, ^K=$0B, and CTRL+I=$09=TAB), which is what the editor's nano-style bindings use. **C= + key emits the PETSCII GRAPHICS set** (`keytab_cbm` in irq.s, v0.2.07) -- the box/bar characters BASIC listings are full of -- **transcribed from the genuine KERNAL's own C= decode table** (`$EC03` in `kernal.901227-03`). Our matrix indexing turned out to be **identical to the KERNAL's** (verified position-by-position; only the modifier slots differ, where it stores flag bits and we store `$00`), so its table drops straight in: sixty-odd graphics codes are not something to transcribe from memory, and `test_keyboard::test_cbm_table_matches_the_kernal` re-checks ours against the ROM so it cannot drift. The **digit row of that same table carries the other eight colours**, so `cbm_color` is gone. One deliberate exception: VICE's symbolic keymap sends host `_` as `@`+C=, so that combination stays underscore (costing only the `$A4` graphic; the ← key gives underscore on real hardware, matrix 57). Displaying them needed `pet2scr` to gain the standard ranges -- **`$A0-$BF` -> screen `$60-$7F`, `$C0-$FF` -> `$40-$7F`** -- which **subsumes the old `$DB-$DD` Swedish special case** (same arithmetic), and CHROUT/readline/the editor to accept `$A0-$FF` (CHROUT still ignores `$80-$9F`: those are control codes, not characters). **CTRL+1..8 emit the first eight colour codes** (`ctrl_color`, v0.2.05), as on a real C64 -- they are control codes with no glyph, so they cannot live in the key tables and are the only way to get a colour into a BASIC string. The editor had to change twice to accept them: its insert filter dropped control bytes, and `scrc` rendered every unprintable as `?`. **`$05` (white) is the exception -- it IS `^E`**, which the editor binds to line-end, so it can never reach the text on its own; **`^V` inserts the next key literally** and settles that whole class (cursor down `$11`, home `$13`, clear `$93` are all legal inside a BASIC string and all bound). Note `^V`'s case must `continue`, not `return` -- `return` is how `^X` quits. It now shows them the way the C64 does inside quotes -- in reverse video, over a screen code **measured against the stock KERNAL** (`test_runstub::test_control_code_glyphs_match_the_kernal`): `$00-$1F` reverse screen code `c`, but `$80-$9F` reverse `(c & $1F) + $40`. The obvious `c & $7F` is wrong -- it maps red (`$1C`) and purple (`$9C`) to the SAME glyph, and likewise the other seven pairs. The glyph still will not match a stock `LIST`, because stock BASIC runs the uppercase/graphics charset and this shell the lowercase one: same code, different font -- so the colours are distinguishable from each other, and any code already embedded in a loaded program is visible too (and round-trips byte-for-byte, since the tokenizer copies inside quotes verbatim). `test_keyboard` asserts the two tables from ROM; `test_edit` injects a code and checks it is stored and drawn reversed (the live matrix is hardware-only, as ever). Without that, the CBM key (a higher matrix code) won the last-key-wins tiebreak and emitted nothing, so shift-minus produced no underscore. Key repeat: a held key re-emits after `KEY_DELAY` (~0.5s) and then every `KEY_RATE` (~15/s), via an `RPTCNT` countdown in the scan (the new-key path arms the initial delay; the held path counts down and re-emits at the rate). `reset.s` now also clears the keyboard buffer count (`NDX`) and `LSTX` at boot. The matrix *scan* (which key is down, SHIFT, repeat) is GUI-verified (`make run`), since the harness injects into the buffer rather than the matrix — but the decode *tables* are checked directly: `keytab`/`keytab_shift` are `.export`ed, ld65's `-Ln build/labels.txt` records their addresses, and `test_keyboard.py` reads the bytes out of ROM and asserts the entries.

Phase 6 (disk I/O) — done and tested: `src/iec.s` bit-bangs the IEC serial bus on CIA #2 ($DD00) — LISTEN/TALK/secondary/UNLISTEN/UNTALK, `iec_sendbyte` (with EOI), `iec_getbyte`/ACPTR (sets EOI in ST=$90). IRQs are masked per byte. **EOI byte gotcha:** at end-of-stream a 1541 clocks out a real final byte (returned with EOI set), but a Meatloaf/SD2IEC just goes idle, so `iec_getbyte` synthesizes a `$00` (no real byte) with EOI. A consumer must NOT store that `$00`: `cmd_cat` `chrout($00)`s it (a no-op), but `edit`'s `load_file` did store it and showed it as a trailing `?` (`scrc($00)` = `?`) -- fixed by only keeping the EOI byte when it's non-zero. The C side uses a one-arg-at-a-time interface (`src/iec.h`). `src/commands/fs.c` reads the `"$"` directory through shared helpers (`dir_begin`/`dir_line`/`dir_end`, streaming the BASIC-shaped listing one line at a time) used by three commands: `dir` (the full 1541-style listing — block count, quoted name, type, blocks free), `ls` (just the file names, **in two columns** -- `COL_WIDTH`=20, left name padded out to the right one, a dangling odd name gets its own row; the header is skipped positionally, since Meatloaf synthesizes type tokens from filename extensions (TXT, D64, ...) that a whitelist would hide; known CBM types color the name via `TEXT_COLOR`/$0286: PRG green, SEQ cyan, USR yellow, REL red, DEL grey, and the **navigable kinds DIR, URL, and disk images (D64/D71/D81..., any D+digit token) share yellow** (you can `cd` into all of them, so they read like the directories they act as -- `type_color` checks the second type char to keep DIR/D-digit yellow but DEL grey, since all start with 'D'; v0.1.71); anything else stays the current color; splat `*` prefixes are tolerated; the color is restored to the default *before* each line's trailing CR, so the newline's scroll-fill and the resting cursor cell stay the default color instead of inheriting the last name's color). **`ls`/`dir` paginate like `less`, armed by CTRL** (`paginate()` in `dir.c`): they free-scroll by default, but **pressing CTRL (`SHFLAG` bit 2) at any point during the listing sets a sticky `paged` flag** -- from then on, every 22 lines they print `-- more --` and wait for a key (`q` quits and emits a CR so the prompt lands on a fresh line; any other key clears + continues). `paginate(&lines, &paged)` checks CTRL on *every* call (per line for `dir`, per row for `ls`), so a brief tap anywhere arms it; when it consumes a held CTRL it also **spoils the CTRL-tap** (writes 2 to $028E, v0.1.72) so releasing the key doesn't emit a TAB into the `-- more --` key-wait and flip the page (vs the earlier version that only checked at the page boundary). This **replaced the old CTRL-hold-to-freeze pause**, which ran over the timed Epyx fast path and let the drive abort the transfer if you stalled too long. To make the wait safe, `ls`/`dir` open the directory over **standard IEC** (`dir_begin(0)`), where the drive simply blocks on the next handshaked byte while you read -- so they no longer use the fast path (only `fload`/`run` do). `pwd` (the current device number and remembered name, then the disk name from the header's quoted title, e.g. `9 fd: TEST DISK`; **pwd first tries the drive's `PWD` command** (`try_pwd` in dir.c): it OPENs channel 15 with `"PWD"` and reads the reply -- Meatloaf and other network drives return the current path directly (idolpx added `PWD` to Meatloaf's `iecDrive` on 2026-07-12, PETSCII on the command channel). A drive without it answers with a DOS status (`"31,SYNTAX ERROR,..."`, two digits + comma) or nothing, which `try_pwd` detects and **falls back** to the old header path: the disk name from the header's quoted title, and on a Meatloaf a reconstruction of the network path from the directory's NFO header lines -- `[<scheme>]` / host / `[PATH]` / path, each split into 16-char quoted chunks that pwd concatenates into `<host><path>`. The fallback reads only the header, so it forces standard IEC -- aborting a fast transfer means draining the whole listing. `test_disk::test_pwd_prints_device_and_disk_name` covers the fallback on VICE's 1541 (which SYNTAX-ERRORs `PWD`); the `PWD`-command success path is Meatloaf-only. `load <name>` reads a PRG to its load address and reports `loaded $XXXX-$YYYY` over **standard IEC** (per-byte handshaked, so bit-perfect). The Epyx fast path is split out into `fload` (explicit). Its timed 2-bit receiver (`_epyx_recv_byte` in `src/fastload_recv.s`) samples each byte on fixed CPU-cycle counts; it was scattering corruption (bogus BASIC line numbers, mangled tokens) because a **VIC-II badline** (~40 cycles stolen on every raster line where `(RASTER & 7) == YSCROLL`, $D011=$1B so YSCROLL=3, in the $30-$F7 window) landing mid-byte slid the sample window off the drive's timed bit-pairs -- `sei` can't stop badlines (they're VIC DMA). Rather than blank the screen (what the real cart does), the receiver **paces around badlines**: the per-byte DATA handshake lets us stall before each byte (the drive blocks on our DATA-high) until the raster sits at an offset $\notin\{1,2,3\}$ from which the worst-case sample window can't touch a badline line -- so the screen stays visible during `fload`/fast `ls`/`dir`. `load` stays standard IEC (bit-perfect, no fast path); `fload` and the fast directory are for speed, and `run <name>` fast-loads via `fload` (see below). See `docs/EPYX-RECEIVER.md`. `dir_begin(allow_fast)` can use the **Epyx fast path** (capable drive) or standard IEC: `dir_begin` picks the source and `dir_line` reads through a unified `dir_getbyte`/`dir_ended` -- the fast source reads the Epyx `[length][data...]` stream a byte at a time, crossing block boundaries transparently (no whole-directory buffer, so a listing never clobbers a loaded program), and `dir_end` drains to the EOF marker so the bus is left idle. **`ls`/`dir`/`pwd` now all pass `allow_fast=0`** (standard IEC) so they can paginate / read the header without a timed transfer aborting; the fast `dir_*` path is dormant but retained (re-enable by passing `allow_fast=1`). (An earlier note here said the dynamic directory *had* to stay on standard IEC because a fast listing garbled; that garble was actually VIC-II badlines corrupting the timed receive, now fixed by the receiver's badline pacing -- see below.) `run [<name>]` starts a program in a real **stock** environment. Given a filename it first fast-loads that PRG over the Epyx path -- the shared `fload_program` helper in `fs.c` (factored out of `cmd_fload`), so `run <name>` == `fload <name>` then `run`; a failed fast load reports and stops. Bare `run` re-runs whatever was loaded last (`load`/`fload`/`run <name>`), or prints "nothing loaded". To launch, it plants a CBM80 autostart stub at $CF00 (`run_stub` in `c_io.s`; above the RBCP/overlay RAM and below RAMTAS's $A000 ceiling), points a CBM80 structure at $8000 to it, writes the program's load address and end/VARTAB to $CFF8-$CFFB, and swaps to the stock ROMs via `rbcp_launch_stock` -- the stock reset autostarts the stub. The stub calls IOINIT/**RAMTAS**/RESTOR/CINT (RAMTAS gives BASIC the clean zero page it needs -- our shell leaves cc65 leftovers -- and its non-destructive RAM test preserves the loaded program), restores `$BA` (current device / FA, which RAMTAS zeroed) from the load device $CFFD so a program reading `PEEK(186)` to choose its drive doesn't hit `?ILLEGAL DEVICE NUMBER` (the device byte a real LOAD leaves behind), then sets a BASIC program ($0801) up exactly the way stock BASIC's own LOAD does ($A52A): init-without-NEW (`$E453`+`$E3BF`), seed VARTAB, `$A659` CLR, then **`$A533` LINKPRG** to rebuild the line-link chain. LINKPRG is essential -- a real PRG's on-disk forward links usually don't match the load address (BASIC's LOAD rebuilds them), so without it RUN hits ?SYNTAX ERROR and LIST shows garbage (this was the FB failure: the bytes loaded correctly, but the unrelinked chain broke BASIC). A mode byte at $CFFC then chooses `$A7AE` RUN (mode 0, `run`) or `$A474` READY. (mode 1, used by `runstock` when a program is loaded, so it lands at stock BASIC's prompt and can be LISTed/RUN by hand -- a bare cold swap would NEW it away). Machine code (load address != $0801) ignores the mode and does `JMP ($CFF8)`. The stub is validated against the real stock ROMs in `test_runstub.py` (skipped if stock-roms/ is absent) -- including a deliberately broken `$FFFF` link that LINKPRG must rebuild before RUN, and the READY-mode no-autorun path. Hardware-only like runstock (the swap is inert in VICE / shell-only builds; `run` then would re-detect the planted CBM80 and loop, so it needs the onerom-stock firmware). Filenames are folded to uppercase (CBM filenames are uppercase PETSCII). No-device gets a "device not present" ($80) timeout; a present-but-silent drive gets a ~1.4s read-timeout ($02) on every CLK wait so a disk-less `ls` prints "read error" instead of wedging. The *send* path is bounded too: `iec_sendbyte`'s first handshake (`@wlisten`, "is a listener there?") waits for DATA via `wait_data_lo` (~0.7s) and sets $80 on timeout — so targeting a device number that isn't on the bus (e.g. `device 9` when only 8 is present) reports "device `<n>` not present" instead of hanging forever, even though the present drive ack's the absent device's command bytes under ATN (the absent device only reveals itself once ATN is released and nobody listens for the name). This is exactly what lets `device <n>` probe-before-switch (above). The remaining send waits (`@wready`/`@eoiack`/`@ack`) stay unbounded so a busy-but-present drive (mid-seek) isn't falsely abandoned. On that send-timeout `send_listen` bails through `@fail`, which broadcasts UNLISTEN+UNTALK (which the present drive acknowledges) so it returns to idle and the next command to the real device works (`test_device.py::test_absent_device_reports_and_stays_put`). Tested against **true drive emulation** (mandatory — our replaced KERNAL means VICE's virtual-device traps never fire): `test/data/test.d64` (regen via `make_test_disk.sh`; its `prog` prints "hello from prog" and RTSes) mounts via `Vice(disk=...)`/`VICE_DISK`; tests poll until transfers finish; `test_run.py` checks `run` prints and then the shell regains the prompt. **(v0.1.81 update to the mode byte above:** `$A7AE` proved unreliable from the raw cartridge-autostart cold state on real hardware — it came up blank — so **mode 0 now auto-types `RUN`+CR into the keyboard buffer and drops into the same `$A474` READY path mode 1 uses**, letting stock BASIC run the program through its own machinery; a one-shot in-stub `$0302`/IMAIN hook `run_imain_hook` skips the pre-RUN READY then swaps back on program end. `test_runstub` runs it against the stock ROMs.) **Getting back to Tardis from stock BASIC** is **RUN/STOP+RESTORE** (the stub points the NMI vector `$0318` at `rbcp_nmi_escape`), or holding **C=** at a One ROM cold boot for the menu. Note this only works after the stub ran (`run`, or `basic` with a program loaded); a bare `basic` cold-swaps, so from there it's a power cycle / C= cold boot. (A typed stock-BASIC `EXIT` command was prototyped in v0.1.83 as an IGONE `$0308` wedge but reverted in v0.1.84: a keyword wedge costs ~50 bytes of the 16KB Tardis ROM minimum, poor value for something that only runs while Tardis is swapped out.)

Phase 6 leftovers (when resumed): the shell's `cd` is wired (drive-side; see File commands above) and the formal KERNAL file entry points landed at the start of Phase 9 (see the "KERNAL entry points" section above and `test_kernal_io.py`). Known limit: a `load` overlapping the shell's working RAM ($C000-$CFFF) would corrupt the loader mid-load (the test program loads at $2000 to stay clear).

Earlier phases (see git history): Phase 4 moved the shell into C; Phase 5 added the parser, dispatch table, and built-ins (`help`/`clear`/`echo`/`ver`/`exit` (later renamed `basic`)); the shell then switched to a lowercase-by-default, ASCII-consistent encoding ($D018 = $16; `keytab` in `irq.s` delivers lowercase ASCII; `pet2scr` in `screen.s` maps lowercase to $01-$1A, uppercase at $41-$5A).

Caveats: tests drive GETIN -> CHROUT by writing the 10-byte keyboard buffer directly, so the keyboard *matrix* decode (including SHIFT) and inputs longer than 10 chars still need the GUI (`make run`) or code review — but the line-editing/cursor logic downstream is fully exercised by injecting the codes directly.

Next Phase 8 chunks (the user is choosing the order): command history (up/down), tab completion, cursor blink, AUTOEXEC, more commands (peek/poke/rm/cp/device/reset/mon), config (colors/prompt).
